# 变更提案: 4x 吞吐与超时治理（端到端）

## 需求背景

当前系统提供聊天式入口，后端以 Flask + 进程内 `JobManager/JobQueue` 执行异步生成链路（2D/3D），前端通过轮询 `/api/job/<id>/status` 展示进度与结果。

已知现状与问题（基于代码扫描与用户反馈）：
1. **并发上限（显式）**：`utils/job_manager.py` 默认 `max_concurrent=5`，同一进程最多同时执行 5 个生成任务。
2. **外部生图吞吐（隐式）**：`banana-pro-img-jd.py` 默认启用全局串行锁 `JD_IMG_SERIALIZE=1`（并带最小间隔），使“外部生图请求”在单进程内近似 **串行**，是当前吞吐的关键瓶颈候选。
3. **超时是最常见失败**：外部模型服务调用（分析/生图/Gate）统一使用较长超时（多为 90s），并存在**多层重试叠加**（urllib3 Retry + 业务层循环重试），容易在 upstream 变慢时导致线程长时间占用，进而放大排队与超时。
4. **状态存储在进程内内存**：任务状态保存在单进程内存中，若使用多进程/多实例部署且无粘性路由/共享存储，`job_id` 查询可能命中不同进程导致“任务不存在”。

目标（用户确认）：
- 先评估现有并发量（结论：Job 级别并发上限为 5/进程；外部生图默认近似 1/进程）。
- 在当前单机资源（CPU 20核 / 内存 120G / GPU 4090）能力上，将吞吐提升 **4 倍**，并显著降低“超时”失败率。
- 允许引入额外组件/中间件（例如 Redis 等），但本阶段优先采用“单机可落地、最小侵入”的方案（方案1），不强依赖新基础设施。

## 变更内容

1. **端到端可观测性（先量化再优化）**
   - 记录每个 Job 的分阶段耗时（analyze / match / compose / decorate / gate / validate），并输出聚合指标（P50/P95、超时率、429率、排队等待时间）。
   - 统一 Trace/Request/Job ID 的透传，便于定位超时发生点与重试链路。

2. **分层并发控制（从“线程堆叠”转为“配额治理”）**
   - Job 级并发：将 `max_concurrent` 从 5 提升到 20（4×），并支持环境变量可配置与动态降载。
   - 外部调用并发：为不同外部能力建立独立配额池（文本分析/配件生图/Gate 审核），取消脚本级全局串行锁，改为可配置的并发 + 速率限制（令牌桶/最小间隔）并尊重 `Retry-After`。
   - 统一“外部调用”入口（复用 `requests.Session` 连接池，避免重复握手/连接风暴）。

3. **超时治理（让系统在慢的时候“慢得可控”）**
   - 统一超时与重试策略：避免多层重试叠加造成指数级耗时与线程占用。
   - 引入 Job 级 time budget：每个 job 设定最大允许时长；超过预算则提前失败并给出明确原因。
   - 熔断与降级：当连续超时/429 超过阈值时，自动降低外部并发或暂时拒绝新 job（503），保护系统整体可用性。

4. **Prompt/分析链路优化**
   - 在“预分析已确认”的链路里复用已有结果，减少重复的敏感检查与分析调用（引入 compliance 缓存/签名）。
   - 移除/替换 `HeadMatcher` 表情中文→英文翻译的额外大模型调用，避免额外外部依赖引发超时。

5. **拼装链路优化（CPU/GPU 资源利用）**
   - 将 OpenCV 拼装等 CPU 密集任务迁移到可复用的进程池（利用 20 核），减少 GIL 影响。
   - 对可复用的静态素材做预计算（红区/关键点/嵌入）并缓存，降低每次 job 的重复计算与磁盘 I/O。

6. **审核/Gate 优化（减少外部调用次数）**
   - Gate 默认路径改为“单模型快速判定”，仅在疑似严重异常时才触发二次裁决（可配置）。
   - Gate 并发独立限额，避免与生图抢占配额导致互相超时。

7. **前端与网络性能优化**
   - 轮询自适应：根据 `queue_position/stage` 动态调整轮询频率，避免大量空轮询压垮后端。
   - 图片静态资源缓存/反代建议：减少 Flask 直接承载大流量静态分发的压力。

8. **部署方式建议（保持状态一致性）**
   - 方案1阶段默认保持“单进程任务状态一致性”，通过提升内部并发与外部配额治理实现 4×。
   - 如需多进程/多机横向扩展，进入下一阶段（方案2）：引入共享任务状态与队列（Redis/Celery 等）。

## 影响范围

- 模块:
  - backend（生成链路、审核、并发与超时治理）
  - frontend（轮询策略与错误呈现）
- 预计涉及文件（按实现阶段逐步落地，不要求一次性改完）：
  - 后端：`app_new.py`、`utils/job_manager.py`、`utils/http_client.py`、`generation_controller.py`、`generation_controller_2d.py`、`banana-pro-img-jd.py`、`gate-result.py`、`content_agent.py`、`matchers/head_matcher.py`、`utils/clip_manager.py`
  - 前端：`frontend/src/components/ChatInterface.tsx`、`frontend/src/lib/api.ts`
  - 新增：`utils/limits.py`（配额池/限流）、`utils/metrics.py`（指标聚合/导出）、`test/perf/*`（压测脚本）

## 核心场景

### 需求: 高并发生成（3D）
**模块:** backend / frontend

#### 场景: 20 个并发用户同时点击“生成”
- 预期结果:
  - 系统能稳定接收请求并返回 `job_id`，排队信息可用（`queue_position/estimated_wait`）
  - 任务成功率显著提升，超时失败率下降
  - 外部调用并发受控，不出现“线程堆叠 + 超时雪崩”

### 需求: 预分析（async）+ 用户编辑后生成
**模块:** backend / frontend

#### 场景: `/api/analyze?async=true` 完成后，用户编辑 `analysis` 并调用 `/api/start_generate`
- 预期结果:
  - 预分析结果复用，避免重复分析/重复合规检查带来的额外超时
  - 仍能保证合规策略不被绕过（基于缓存/签名/阈值校验）

### 需求: 2D 底图直入生成
**模块:** backend / frontend

#### 场景: 2D 编辑器生成 `base_image_url` 后启动 2D 生成
- 预期结果:
  - 跳过匹配与拼装步骤，直接进入配件/背景/Gate
  - 在高并发下仍能保持可控的外部调用并发，不因跳过步骤导致“外部请求陡增”而超时

### 需求: Gate 在高负载下可控
**模块:** backend

#### 场景: 系统负载高（超时/429 升高）时 Gate 自动降级
- 预期结果:
  - Gate 能根据水位选择“快速判定/采样/强审核”
  - 质量与吞吐之间可配置、可回滚

### 需求: 失败可诊断
**模块:** backend / frontend

#### 场景: 任一阶段超时或失败
- 预期结果:
  - 返回明确的失败阶段、错误分类（timeout/429/invalid_input/unknown）
  - 生成记录与指标能定位瓶颈点（外部调用、拼装、Gate、队列等待）

## 风险评估

- **风险:** 并发提升触发 upstream 限流（429）或更高超时率  
  **缓解:** 外部配额池（并发+速率）+ 尊重 `Retry-After` + 自动降载/熔断
- **风险:** Gate 降级影响质量  
  **缓解:** 分层开关、采样策略、仅在高水位降级、可一键回滚到强审核
- **风险:** 多进程部署导致 job 状态丢失  
  **缓解:** 方案1明确保持单进程状态一致性；需要横向扩展时进入方案2（共享任务存储与队列）
